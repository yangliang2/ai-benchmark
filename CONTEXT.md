# Domain glossary

The vocabulary this project uses. Skills and contributors should use these terms exactly; synonyms noted as "not: …" are deliberately avoided.

## Core concepts

- **Unified dataset** — the single store all three layers read and write: one JSONL file of validated **records**. It is the project's only test seam (not: database, results table).
- **Record** — one row of the unified dataset: one **combination**'s result on one **benchmark instance**, or an aggregate result when per-instance data is unavailable. Machine-readable schema: `ai_benchmark.schema.Record` (see ADR-0001).
- **Combination** — an agent × model pairing, e.g. claude-code × claude-sonnet-5. The unit being evaluated (not: setup, config).
- **Agent** — the coding harness/scaffold (claude-code, aider, cursor, …), independent of the model driving it (not: assistant, tool).
- **Benchmark instance** — one task inside a source benchmark, e.g. one SWE-bench issue (not: problem, sample).
- **Capability matrix** — the conceptual grid task category × combination × dimension the whole project exists to fill. Empty cells are as informative as full ones.
- **Quality metric** — the named measure a record's quality value is expressed in (e.g. `resolved`, `resolution-rate`, `pass-rate`). Values under different quality metrics are never directly comparable (not: score).
- **Pareto frontier** — within one task category, the set of combinations not dominated on both quality and cost.

## Task taxonomy

See ADR-0002 for why categories are shaped this way.

A **category** is one **engineering action** — what is done, never what kind of ticket the work arrived as, and never where it happens (that is the **surface** annotation). Every benchmark instance and first-party eval task is classified into exactly one category: a benchmark task measures **exactly one action**, because it needs one gradeable deliverable. A *real* ticket is a **sequence** of actions — investigate, then edit, then test — and that relation is documented here rather than keyed on: there is no multi-label category and no category tuple, and when several actions apply the **primary deliverable** of the task decides which one it is filed under.

- **bug-fix** — correct existing behaviour that is wrong.
  Includes: SWE-bench-style issue→patch tasks; regression fixes.
  Excludes: adding a missing capability someone filed as a "bug" (feature-dev); making newly written tests pass (test-authoring or feature-dev).
- **feature-dev** — add new user-visible capability.
  Includes: new endpoints, commands, options; extending behaviour to new cases.
  Excludes: pure restructuring (refactor).
- **refactor** — behaviour-preserving restructuring.
  Includes: renames, module splits, interface reshaping with unchanged behaviour.
  Excludes: any change with intended behaviour difference (bug-fix or feature-dev).
- **test-authoring** — tests are the primary deliverable.
  Includes: writing missing tests for existing behaviour; hardening flaky tests.
  Excludes: tests written incidentally while implementing a feature (feature-dev).
- **codebase-comprehension** — answer questions about code without changing it.
  Includes: explain-this-module, how-does-X-work.
  Excludes: any task whose deliverable is an edit; saying where a defect lives (fault-location).
- **fault-location** — say where a defect lives, without fixing it.
  Includes: naming the file and symbol a reported failure comes from.
  Excludes: producing the fix as well (bug-fix).
- **code-review** — judge a diff someone else wrote.
  Includes: finding the defects in a change, with their locations.
  Excludes: applying the corrections (bug-fix or refactor).
- **investigation** — investigate an open question and propose an answer.
  Includes: options with trade-offs, a recommendation.
  Excludes: questions answerable by reading one module (codebase-comprehension).
- **requirement-decomposition** — break a requirement into workable pieces.
  Includes: turning an ask into ordered, independently deliverable steps.
  Excludes: delivering any of the pieces (whatever action that piece is).
- **performance-optimisation** — make existing behaviour faster or cheaper.
  Includes: hot-path rewrites, algorithmic replacement, measured against a baseline.
  Excludes: restructuring with no performance target (refactor).
- **unclassified** — not yet classified, or genuinely unclassifiable. Never force-fit; count of unclassified instances must stay visible.

Machine-readable, and the one definition the record schema, both task models and the classifier's prompt all read: `ai_benchmark.schema.TaskCategory`. `frontend-ui` and `infra-config` were categories until round 4 and are no longer: they named *where* work happens, so a frontend bug fix had to pick one of two boxes. They are `surface` values now, and a record or task still naming one is refused with the value it became.

## Task annotations

Orthogonal to category:

- **scale** — `single-file` (edits confined to one file), `cross-file` (edits span files), `unknown`.
- **surface** — where the work happens, as against what is done: `application`, `frontend`, `infrastructure` (build, CI/CD, deployment, dependencies, configuration), `unknown`. Optional everywhere, defaulting to `unknown`, so no stored record or task needed migrating when it arrived. Not part of any row key: the calibration view keys on category, and a surface is disclosed rather than grouped by.
- **language** — primary language of the task's repo (lowercase, e.g. `python`, `typescript`). On a stored record it is optional, absent when not meaningful, because an external benchmark need not disclose one. On a **first-party v1 task** it is **required**: the declaration is what selects the **language runner** that grades the task, so a task without one has no grader and is refused at load rather than defaulted.

## Classification vocabulary

- **Label** — the classification verdict for one benchmark instance: a task category plus the task annotations (scale, language). Labels fill gaps in a record; they never overwrite source-derived facts (not: tag, annotation set).
- **Classification cache** — the committed JSON file keyed by `benchmark/instance_id` holding one label per instance. A warm cache makes classification deterministic and free; an unclassifiable verdict is cached too, so it is never re-asked and never force-fitted.
- **Instance context** — the committed JSON file (`data/instance-context.json`, keyed like the classification cache) holding what an instance actually asked for: its **problem statement** and the **patch file list** (files changed by the reference solution). The problem statement is classifier evidence; the patch file list makes scale mechanical (one file → `single-file`, several → `cross-file`) with no LLM call, and a mechanical scale always beats an LLM guess.

## First-party eval vocabulary

- **task set** — the checked-in collection of first-party benchmark instances (the file `tasks/first-party-v0.yaml`; the directory `tasks/first-party-v1/`). Versioned as a whole; its name is the benchmark name.
- **task** — one first-party benchmark instance. v0: a self-contained prompt plus a **check**. v1: a **task directory**.
- **check** — the static regex that grades a run's final output as resolved or not. v0 limitation: checks demand task-specific content but do not execute anything, so `resolved` on a first-party-v0 record is pattern-verified — weaker evidence than SWE-bench's test-verified `resolved`. Grouping by benchmark keeps v0, v1 and SWE-bench from ever pooling.
- **run** — one task × combination execution with exact measurements (tokens in/out, cost USD, latency, turns) as reported by the **agent adapter** that ran it — what a measurement is made of is the harness's, so a second adapter can measure what its own CLI reports rather than what claude-code's does, and how `cost_usd` was obtained is disclosed on the row as its **cost source**. A v1 run also carries its **workdir diff**.
- **live run-time limit** — how long one **v1** live **run**'s agent may take before the v1 live runner kills it and the run fails loudly; it does not reach the runner's own git plumbing (`_commit_pristine`, `_capture_workdir_diff`), which carries its own fixed 60-second timeout untouched by this table, and it does not reach v0's live runner, which still hardcodes the flat `RUN_TIMEOUT_S` (reachable via `ai-bench eval --live`). Set per task class in one registered **tier table** in code (`ai_benchmark.firstparty_v1.LIVE_RUN_LIMITS_S`), keyed on **category** and read by the v1 live runner; a class with no deliberately-set limit falls back to the flat 600 seconds, which is where every category still sits. Keyed on category because the **task-set lint** already holds every member of a **task family** or a **pair** to one, so for those two constructs "every member of one contrast shares one limit" holds by construction rather than by an author's discipline; a contrast whose members differ in category — a locate/fix comparison over one planted defect, whose members are declared neither a family nor a pair for exactly that reason — is not held to one limit by this key, and tiering fault-location and bug-fix differently would confound exactly that comparison. Registered before the sweep that reads it and never adjusted per cell inside one — which is why a caller cannot pass one: raising the limit for the one cell about to hit it spends that cell, only ever swept once, under conditions nobody chose in advance. A limit that changes between **round**s is a cross-round caveat, recorded beside the round the way a CLI version change is — narrated only, since a **run** carries no limit field; every round so far ran at the flat default, so the note determines the ceiling for any row in the log, and the first registered tier is the point at which one sweep's rows would run under different ceilings and the limit has to be stamped on the row instead. Round 4 registers `bug-fix` and `fault-location`, both at 600 — the flat default's own value, chosen because its locate/fix contrast spans the two categories that would confound if tiered apart, so equal registration is the move that clears that constraint rather than the one that violates it; no cell moves and the limit stays a narrated one, not a stamped one (design note §37).
- **raw run log** — JSONL, one row per run, appended as each run completes. The provenance boundary: live runs write it, evaluation and replay only ever read it, and a record's source is the log itself. Each row the *v1* runner writes also names the **round** it belongs to, by carrying that round's sweep id (a v0 row has no such field at all); v1 rows written before the field existed carry none, and stay valid and replay-exact without it.
- **agent adapter** — the runner code that drives one **agent** headless and turns its output into a **run**: invocation, event parsing to turns/tokens/latency, version capture, the permission-denial equivalent, the **live run-time limit** — which it is handed and never chooses. `claude-code` is the first; `codex` the second. Adding an agent adds a column to every cell and is an instrument in its own right (not: model, backend). Lives in `ai_benchmark.agents`: one adapter per harness, a registry keyed by the name a row's `agent` field carries, and a name with no registered adapter refused by the v1 live runner before anything runs — `ai-bench eval-v1 --live --agent` names it, defaulting to `claude-code`. Everything around the run stays the runner's: the fresh workdir, the pristine commit, the **workdir diff**, the sweep id, the log append.
- **list-price equivalent** — what every `cost_usd` in this project means, whatever the account was billed: **the vendor's published API unit price × the tokens the run used**. A subscription login (ChatGPT for Codex, a Claude plan for claude-code) changes the invoice, not the number — the number is what the same work costs on the metered API, and it is the one figure two harnesses, two models or two rounds can be compared on. So a `vendor-reported` figure printed by a CLI and a `table-derived` one computed from a **price table** are both list-price equivalents; the **cost source** says how each was obtained, not whether anyone was charged. Pre-registered cost ranges are stated in the same currency, and are estimated **from tokens at API unit prices** — input priced with the cached/uncached split the account would actually see, output at its rate — never from "what the subscription costs". *Ruled 2026-08-19 by the owner after round 6's record (§54) read its $2.15 as "not an invoice": the invoice is beside the point; the estimate is the metric.*
- **cost source** — how a run's `cost_usd` was obtained: `vendor-reported` (the agent's own USD figure, as claude-code prints) or `table-derived` (tokens × a **price table**). Disclosed on the run so cross-agent cost readings say the two numbers were made differently: `cost_source` and, for a table-derived figure, the `price_table` version ride on the **v1** raw run log row (`ai_benchmark.firstparty_v1.Run`) as two optional fields, absent on every row written before they existed and still valid and replay-exact without them; v0's row is untouched, since no Codex row is ever written to a v0 log. A row is refused at load if it contradicts itself: a `codex` row naming neither `table-derived` nor a price table, a `vendor-reported` row naming a price table, or a `table-derived` row naming none. Each **agent adapter** stamps its own `cost_source` (and `price_table`, where it has one) on every row it builds; claude-code stamps `vendor-reported` and no price table. Nothing recomputes cost, on load or on replay: `cost_usd` is whatever the row says, and a later price table version reprices nothing already logged.
- **price table** — a checked-in, as-of-dated table of per-token prices per model, used only where an agent reports tokens and no dollars. Its version rides in the **raw run log** beside `agent_version`. Checked in as data at `data/price-table.json` (version, as-of date, source URL, pricing tier, and per-model uncached-input/cached-input/cache-write-input/output per-token prices — four prices, since the published page prices a cache write separately from a cache read), loaded and priced by `ai_benchmark.pricing`. Priced at the **standard-short-context** tier: the published page also carries Batch and Flex tiers and a long-context column, none of which `codex exec` runs at.
- **instance-level** — umbrella for the two source types that carry per-instance rows and may pool into rates (`per-instance`, `first-party`). Rows of different source types never pool together (ADR-0001).

### v1: execution-verified grading

- **task directory** — one v1 task: `task.yaml` (id, category, scale, surface, language, prompt, grading config, and — where the task carries an **accepted-answer key** — its `domain_nouns:` and any **terrain waiver**), `repo/`, and `grading/` — plus, on a **code-review** task, the `corrected/` tree the author's fix lives in, and, on any task whose **existence proof** is a test, the `proofs/` subtree those tests live in. Both sit beside `repo/` rather than inside `grading/` because that directory is overlaid into the workdir wholesale, and the loader refuses either found under it: that is what makes "never overlaid, never collected, run by the lint only" a property of the layout rather than of an author remembering it.
- **starting repository** — the `repo/` directory, a small hand-authored repo copied fresh into the agent's workdir, built under the **stdlib-only rule** (ADR-0003) for the task's own **language**. What the agent sees and edits. For a Python task, its top-level modules must **not be named after standard-library modules** (no `queue.py`, `types.py`, `calendar.py`) — the loader rejects such a task. Grading keeps the standard library ahead of the workdir on `sys.path`, so at grade time such a module is invisible, the standard-library one is imported instead, and the task is unsolvable however good the agent is. The loader has to enforce this because the lint cannot see it: when the standard-library module does not happen to satisfy the grading tests, the task fails pristine exactly like a good task, lints clean, and then grades every agent unresolved — indistinguishable from a merely hard task. For a TypeScript task, the same rule is enforced differently: an import may only name a `node:` builtin or one of the task's own files, reached relatively and with its extension — no `package.json` and no `node_modules` anywhere in the repository, both refused by the loader at any depth — and a keyed task's `repo/` must additionally be flat, which is what makes the hash gate over its bytes actually gate.
- **grading tests** — the held-out tests in `grading/`, which the agent never sees. Canonical: at grade time they are copied *over* the workdir, so a file the agent wrote at a grading test's path is overwritten. They must be **self-contained**: grading runs with conftest loading disabled and its pytest config pinned outside the workdir, so a grading test that relies on a `conftest.py` will not work (and the task-set lint catches it on the pristine repository).
- **workdir diff** — the graded artifact of a v1 run: the workdir's full diff (modified, added and deleted files) against the live runner's initial commit of the pristine starting repository, captured as `git add -A` + `git diff --cached --binary` against that commit's recorded id, with the operator's global and system git configuration masked out so the artifact cannot vary with the machine. A runner-owned `.gitignore` (`__pycache__/`, `*.pyc`, `.pytest_cache/`), written before the initial commit and restored before capture, keeps test-run byproducts out of the diff and never itself appears in it (which is also why a task may not ship its own). What makes replay exact; a v1 run's final message is metadata, not evidence.
- **execution-verified** — the v1 grading standard, replacing v0's pattern-verified checks: copy `repo/` to a fresh temp directory, apply the run's workdir diff, overlay `grading/`, run the grading tests with a timeout. `resolved` is 1.0 iff every one of them ran and passed — the same standard as SWE-bench's `resolved`.
  The verdict ignores what the agent wrote *around* the grading tests. pytest runs with `--noconftest` and a config pinned outside the workdir, so `conftest.py` hooks and `addopts` smuggled through `pytest.ini` / `tox.ini` / `setup.cfg` / `pyproject.toml` can neither forge a pass nor sink a correct solution; the workdir is kept *behind* the standard library on `sys.path`, so a file the agent added cannot shadow a stdlib module a grading test measures against; and the verdict reads a test report written outside the workdir rather than the exit status alone, so a run that ends before the tests finish cannot pass by accident.
  Accepted limitation: grading executes agent-written code in a **local subprocess with a timeout, not a sandbox** — the same exposure as any local SWE-bench-style eval. The live run is part of the same stance: headless claude-code auto-denies tool use not granted up front, so the v1 runner grants the agent full tool use (`--permission-mode bypassPermissions`) inside its throwaway workdir — a narrower per-tool allowlist was tried first and aborted a real sweep when a model read outside its workdir, and behaviour-driven denials recur on retry; a run the environment still blocked (non-empty `permission_denials`) is a broken run and fails loudly rather than logging a verdict. **The boundary this draws:** those defences stop an honest-but-messy agent, not a deliberately adversarial one — grading runs the agent's code in the same process tree as the oracle, so code that means to can still reach the report the verdict is read from and forge a pass; ruling that out needs process-level isolation, which this grader does not have. Node grading is the same local subprocess stance, not a new exposure: starting repositories are **stdlib-only per language** (ADR-0003), so grading needs no network and no installs whichever language a task declares.
- **behaviour tests / structural assertions** — the two halves of a refactor task's grading suite. Behaviour tests, named explicitly in `task.yaml`, assert the behaviour the restructuring must preserve; every other grading test is a structural assertion that the restructuring actually happened.
- **answer file** — the structured file a task whose deliverable is prose rather than a code change asks the agent to write into its workdir, at a path the prompt names — **fault-location**'s first, then locate-style **codebase-comprehension**'s and **code-review**'s. It reaches grading with no new seam and no new machinery — it lands in the **workdir diff** like any other file the agent wrote, the existing pipeline applies that diff and overlays `grading/`, and a held-out grading test reads the file back and compares it against the key its action is graded by — the **accepted-answer key**, or, for **code-review**, the **findings key**. So `resolved` stays **execution-verified** rather than pattern-verified, and the provenance boundary does not move: the run log still stores the agent's final message and the verdict still never reads it. Replay, the **task-set lint**, **reconciliation** and the **calibration view** inherit the action unchanged. Where the deliverable is one location — **fault-location**, locate-style **codebase-comprehension** — it names **exactly one (file, symbol) pair and never a list**: the task measures whether the agent located the fault, and a shotgun of every plausible location would be breadth rewarded as accuracy. A **code-review** answer file *is* a list, one location per finding, because a review names as many findings as the change holds; there the shotgun is refused by the **findings key**'s rejected half instead, and a finding may carry a free-text note the verdict never reads. What the comparison forgives is spelling, not identity — surrounding whitespace, a leading `./` and a trailing `()` are stripped, and a bare symbol matches the last dotted component of an accepted one (`total_with_tax` answers `Basket.total_with_tax`), while file and symbol stay case-exact, because Python is and because a case-insensitive match would make a verdict depend on the filesystem the grader ran on.
- **answer comparison** — `grading/_answer.py`, the module that reads the **answer file**, normalises it and matches it against the **accepted-answer key**. It ships identically into every fault-location task's grading directory and the **task-set lint** reads the copies byte for byte against the bytes this project itself owns — a *stronger* check than the one it runs on a **task family**'s starting repositories and grading suites, which compares each member's tree against the alphabetically-first member's peer to peer, because a lone fault-location task has no sibling to compare against; both exist for the same reason, that self-containedness beats deduplication and copies drift silently, but only this one has a privileged source to compare against. The held-out grading test that asserts over it is a one-line assertion over `answer_problem()`, and is itself shipped and byte-compared the same way (`grading/test_answer.py`), because shipping the module byte-identical proves nothing about whether a task's grading test actually calls it — nothing did, until a task's grading test was made to earn that too. Both are owned rather than hand-written per task because the half of the verdict that discriminates is the half worth not miscopying.
- **accepted-answer key** — a fault-location task's ground truth, a data file (`grading/accepted-answer.json`) declaring the **answer file**'s path and the set of accepted answers. It ships *inside* the held-out grading directory, so it reaches the workdir by the overlay that already copies that directory wholesale and is never collected, collection globbing test files only; the lint reads the same file from the task directory. **Held out means held out of the workdir, not of the machine**: the agent's workdir carries the starting repository and nothing else, but the key is a plaintext file on the same filesystem and the v1 runner grants full tool use. That exposure is not new — every task's held-out grading tests are equally readable — but the payoff is, because for this action the key *is* the whole deliverable rather than a shortcut to producing one, and reading it leaves no trace the log would carry. Hashing the accepted pairs would be theatre: the (file, symbol) space of a small hand-authored repository is enumerable and the salt would ship beside it. So a fault-location verdict rests on the stated assumption that the agent did not read the key off disk, and closing that properly means running the agent where the checkout is unreachable — a property of the runner, owed to every task and not just these. An accepted answer is a **(file, symbol) pair and never a line number** — lines shift under any edit and equally-correct answers land on different ones — and a key naming one is refused at load. The author writes down every description level that is legitimately correct, typically the defective function and the class enclosing it (a method is written `Class.method`, and either spelling answers it), and the grading test accepts any member of the set. A symbol is a `def`, a `class`, or a module-level assignment — so a fault in a constant, a dispatch table or a compiled pattern can be named — but never a file alone: on repositories as small as these a bare filename is barely a location, and would resolve for an agent that located nothing. That set is the mitigation for this grading's one expensive assumption, that an agent which correctly locates a fault describes it at a level the author anticipated: it is the author's judgement rather than a mechanism. The lint checks what the set can show — that it accepts something, that every file it names is in the **starting repository**, that every symbol it names is defined in the file it names, that the declared answer path lands inside the workdir and collides with nothing the overlay copies over it, and that the prompt names that path as a whole token, so a task cannot be unsolvable because the agent was never told where to write.
- **rejected answers** — the negative half of an **accepted-answer key**, and what makes a fault-location verdict mean something. The **must-fail-on-pristine** invariant cannot do that job here: a pristine repository carries no **answer file**, so grading fails it unconditionally and the check proves nothing — a grading test that reads no key at all, or a task with no defect in it, satisfies it. So the **task-set lint** runs answers it expects to *fail* through the real grading pipeline and demands unresolved. Four it constructs itself, needing nothing from the author: a missing answer file, an empty one, a malformed one, and an accepted file paired with a symbol the key does not accept. That last one is the load-bearing one — it is what a grading test which never consults the key, or which checks the file and not the symbol, cannot survive; and where the constructed answer turns out to be a legitimate description of the fault, the lint fails and the author adds it to the accepted set, which is the expensive assumption being paid down by a mechanism instead of by hope. The author supplies the rest, required non-empty, for the near-miss no lint can invent: the plausible wrong *file* — the caller of the defective function, the module that looks responsible. **What proves a defect exists at all is the task's registered *existence proof***, which for this action is the paired `bug-fix` task, whose held-out tests must fail on the same pristine repository. That pairing is a checked relation and no longer a convention: the two members are deliberately neither a **task family** nor a **pair**, so there is no declared link to read, and the lint finds the partner by the bytes of the starting repository the two share and runs it.
- **findings key** — a **code-review** task's ground truth, a data file (`grading/findings-key.json`) declaring the **answer file**'s path, the accepted set of **planted findings** and the rejected set of plausible non-findings: the set-shaped counterpart of the **accepted-answer key**, shipped and held out the same way, and built out of the same (file, symbol) pair with the same refusal of a line number and of a bare file. Its two halves are shaped differently, and that asymmetry is the verdict's own: `rejected` is a flat set of locations, while `accepted` is a set of **planted findings**, each of them a set of alternatives. A run is resolved only if every planted finding is matched — at any one of its alternatives — by some finding in the **answer file**, and no answer matches a rejected finding; answers matching neither are archived, not scored — a real problem the author did not plant must not fail the run, while every-line-is-a-finding still fails on the rejected half. The verdict is binary — partial recall is not a score (not: rubric, checklist). What differs from the accepted-answer key is the quantifier and nothing else: a locate verdict asks whether the one answer is *in* the accepted set, a review verdict asks whether the answer's findings *cover* it, each finding at some accepted level. Every location the key names, across both halves and every alternative, is distinct **through the comparison** rather than merely unequal — a bare-symbol alternative that also answers another finding's qualified one would let a single answer satisfy two findings — and a key naming one twice is refused at load. So the comparison is its own owned module (`grading/_findings.py`, with its one-line held-out test `grading/test_findings.py`, both shipped byte for byte the way the **answer comparison** and its test are) while the *forgiveness* is not: `_findings.py` imports `_answer.py`'s, and ships it beside itself, so a review answer and a locate answer forgive the same spellings.
- **planted finding** — one defect the author put into the change a **code-review** task hands the agent, together with where it is: **a set of alternative locations, matched if an answer matches any one of them**, written `{"any": [ {file, symbol}, … ]}` and non-empty. The **first alternative is the primary** — the most specific location, typically the defective function — and is what the finding is named after wherever a name is needed, its **existence proof**'s file name and every lint message alike, so adding an alternative renames nothing. The set is this action's half of the mitigation an **accepted-answer key** already carried: the author writes down every level that legitimately describes the one defect, typically the defective method and the class enclosing it, and the lint proves the mitigation rather than trusting it — it runs the answer reporting each finding at each of its alternatives through the real pipeline and requires **resolved**. A planted finding was one flat location until round 5's first review task was authored: with the accepted half read under *every*, a second entry for one defect demanded that the answer report it twice, at both levels, so the author keyed each finding at one level and wrote in `task.yaml` why. The alternatives are what that comment was working around. The change the findings live in **lives inside the starting repository**: `repo/` ships it already applied, plus a unified diff of it as a file the prompt names, so there is no second tree the agent can see. The author's **corrected tree** — the repository with every planted finding put right — ships in its own subtree of the task directory beside `repo/` and outside `grading/`, which is overlaid into the workdir wholesale; it is read by the lint and never by grading. Each planted finding carries its own **existence proof** — one per finding, not one per alternative, because a finding is one defect however many locations describe it.
- **existence proof** — the mechanical evidence, checked by the **task-set lint** and never by grading, that a planted truth is really there. Every other gate a keyed task passes asks whether its grading tells a right answer from a wrong one; this asks the prior question, whether there is anything to find. Its form is **registered per action**, one entry per action that carries a key (`ai_benchmark.firstparty_v1.EXISTENCE_PROOFS`), and an action carrying a key with no registered form is refused rather than exempt — so a fourth cannot be added without saying what would prove its truth exists. For **fault-location**, the partner **bug-fix** task's mandatory pristine failure, the partner discovered by the bytes of the **starting repository** the two share because they are deliberately neither a **task family** nor a **pair** and so declare no link; for **code-review**, a held-out test per **planted finding** that fails with the reviewed diff applied and passes on the author's **corrected tree**; for locate-style **codebase-comprehension**, that the accepted (file, symbol) resolves in the **starting repository** — already a rule of the key, registered as this action's form rather than left an unstated exemption. Where the proofs live is what keeps them the lint's and never grading's: a proof test sits in its own subtree of the task directory beside the corrected tree and **outside `grading/`**, which the loader enforces, so nothing overlays one into the workdir or collects one as a **grading test**. Replaces the pairing *convention* under which round 4's fault-location tasks were authored beside a bug-fix partner (not: attestation).
- **terrain rule** — one of the three authoring invariants the **task-set lint** holds every task carrying a key to — an **accepted-answer key** or a **findings key** — so that locating the fault is reading rather than grepping: the prompt names no file and no symbol from either half of the key; no content word or adjacent word pair of the prompt appears only in the module the accepted answer names (matched on word boundaries, with a test file counted as part of the module it tests and `README.md` as no module); and an accepted class-level location comes from a file defining more than one class, since an answer at class level in a one-class module is determined by the filename alone. The narrowing rule reads **the keyed task's own prompt only** — never a sibling task's, however much repository they share. What it forgives is the vocabulary a prompt cannot help sharing with its subject: the closed-class **function words** are owned once in code (`ai_benchmark.firstparty_v1.FUNCTION_WORDS`), and the **domain nouns** are declared per task as `domain_nouns:`. Keyed on the task carrying a key and not on the category, nor on which key it carries: a locate-style **codebase-comprehension** task is graded off the same file and is greppable in exactly the same way, and a **code-review** task's **findings key** names the very locations its **answer file** has to report, so all three are read over both halves of whichever key the task ships.
- **terrain waiver** — a per-task declaration, with a reason, that one named **terrain rule** of the **task-set lint** does not apply to it: `terrain_waiver:` in `task.yaml`, naming the rule, the exact words or `file.py:Symbol` locations it covers, and why. The only sanctioned way past a terrain rule; the rule itself is never loosened, because a loosened rule is loosened for every task authored after it while a waiver costs a written reason in the one file it sits in. Two properties keep it a declaration rather than a mute button: it applies **only to what it names**, so a waived word does not silence the rule for a different word; and **a waiver naming something the rule did not fire on is itself a lint problem**, so it cannot rot silently once the terrain it apologised for is improved. The corpus carries one, on `paperround-locate-the-carried-over-count`.
- **task-set lint** — the authoring invariants, checked before any paid run. Most are checked by running the grading tests on the pristine starting repository: grading tests must fail pristine (nothing is left to do otherwise), and a refactor task's behaviour tests must pass pristine (only its structural assertions may fail). A **fault-location** task's grading also runs several synthetic *non*-pristine diffs — a missing, empty and malformed **answer file**, an accepted file paired with a non-accepted symbol, and every one of the author's **rejected answers** — each graded through the real pipeline and required to come out unresolved, because must-fail-on-pristine alone proves nothing for this category: a pristine repository never carries an answer file, so that check is unconditionally satisfied. A **code-review** task earns the same thing for its **findings key**, read first and then run, and every read rule runs per **alternative** of every **planted finding** rather than per finding — an alternative the repository does not hold is one no answer can reach, and the mitigation would be a line shorter than it reads. Read: both halves say something, every location names a file of the **starting repository** that the shipped diff of the **change under review** actually touches and a symbol that file defines, the findings comparison and its held-out test are this project's own bytes, and the declared answer path reaches the verdict and is named by the prompt (that no location is named twice, within a finding, across two, or in both halves, is refused at load instead, since `run-live` loads a task set and never lints it). Run: the three above plus the four a *set*-shaped verdict has to earn — every planted finding but one, dropping a whole finding and every alternative of it; every planted finding with one of them described by a symbol the key registers on neither side, synthesised per finding per alternative's file; every planted finding plus a rejected one; and each rejected finding on its own. Plus the one **positive** the alternatives exist for: reporting any finding at any of its alternatives, the others at their primary, is required to grade **resolved**, so the mitigation is proved rather than trusted. Every task carrying a key of either shape is also held to its action's registered **existence proof**, and to the three **terrain rule**s, read rather than run, and to the shape of any **terrain waiver** it declares against them. The rest are read from **construction** metadata rather than run — a task outside the **zero-knob baseline** must declare either one or itself a **declared control**, a baseline task must declare no construction, and a **task family** must be one underlying change with exactly one knob moving across it.
- **reference solution** — a full solved copy of a task's starting repository, proving the task solvable: the test suite grades every checked-in task's reference solution `resolved` (and the empty diff unresolved) through the same execution-verified pipeline real runs go through. Lives in `tasks/first-party-v1-solutions/<task-id>/`, outside the task directory, so the loader, the runner, the lint and pytest collection never see it and it can never reach the agent.
- **coverage table** — the count of tasks per `category × surface × language` cell, printed by the **task-set lint**. `scale` and **substrate** are disclosed on a task but not gridded. The table reports; it does not steer — whether a round must fill a cell is that round's spec's acceptance criterion, never a per-task rule. Every **category** appears, including one with no tasks in any language (`test-authoring`, disclosed as `0` rather than omitted). There is no undeclared-**language** column: a first-party v1 task must declare one, because that declaration is what selects the **language runner** that grades it.
- **language runner** — the per-language half of **execution-verified** grading: how a task in that language runs its **grading tests**, yields a machine-readable verdict, lets held-out tests override visible ones, and closes verdict forgery. Python's is pytest with junitxml. Admitted only under the **stdlib-only rule**: a task in the language must be gradable with the language's own toolchain and nothing installed (TypeScript: `node:test` with the JUnit reporter; no `node_modules`). The rule is what keeps grading hermetic without a sandbox (ADR-0003).
- **stdlib-only rule** — the admission condition for a **language runner**: a task in the language must be gradable with the language's own toolchain and nothing installed — no package manager step, no network fetch, no vendored dependency tree. What keeps grading hermetic without a sandbox, and what keeps process-level isolation (#15) unscheduled through the corpus widening to a second language. See ADR-0003.
- **mutation gate** — **test-authoring**'s grading mechanism (lands with round 8): two gates over the test suite the agent wrote at the test path the prompt names, collected from the **workdir diff** as that subtree alone — every edit outside it is archived, not scored, so a source edit can neither rescue a failing suite on gate 1 nor overwrite a mutation on gate 2. Gate 1: the suite passes on the unmodified **starting repository** — no exceptions, a single failure on correct code is the false accusation the **findings key**'s rejected half refuses elsewhere. Gate 2: on each **planted mutant**, at least one test fails. `resolved` is both gates, binary; a kill rate is not a score — the findings key's quantifier, pointed at mutants: every planted mutant killed, by any test. The suite runs under the **language runner** the task declares; the gate itself is language-free. The **terrain rule** does not apply, as an action-level exemption rather than a per-task **terrain waiver**, because the reason is the action's and not any task's: the rule stops a key being grepped out of the workdir, and a mutant is never in the workdir; the prompt naming the module under test is the task's definition, not a leak.
- **planted mutant** — one variant of a **test-authoring** task's **starting repository** carrying one deliberate behaviour change the author designed by hand — a flipped boundary, a dropped condition, a wrong default — this action's key, held out with the same status **grading tests** have always had: on the machine, never in the workdir, never disclosed by the prompt. A mutant patch touches only source files and never the prompt-named test path, and the **task-set lint** checks the disjointness. Its **existence proof** (the registered form for this action) is the author's reference suite, shipped in the task's own subtree outside `grading/`: it passes on the pristine repository and fails at least one test on every mutant, checked per mutant — which is what refuses an *equivalent mutant* (a change no behaviour distinguishes) at the lint, where under the universal verdict it would otherwise make the task unresolvable for every agent. Four to six per task, lint minimum three; spreading them across distinct specified behaviours is authoring judgement, not a lint rule — one test may kill several mutants, since the quantifier binds mutants, not tests.
- **instance-level** — umbrella for the two source types that carry per-instance rows and may pool into rates (`per-instance`, `first-party`). Rows of different source types never pool together (ADR-0001).

### Knob-experiment vocabulary

Task construction as experimental design: a task's difficulty is meant to come from named, independently settable causes rather than from whatever the author happened to write. Defined in full in `docs/design/task-difficulty-and-ex-ante-profiles.md` sections 8–10.

- **knob** — one named, independently settable cause of difficulty, `K1`–`K12`, each traceable to a step a human architect actually performs (K1 decision openness, K8 safety-net quality, K9 crux depth, …). A task **activates** a knob at a **level**; K1's, K8's, K9's and K12's levels are enumerated ladders, the rest are recorded as written until the experiment pins them down (not: dimension, factor). K9's ladder is two rungs, because that is what the design note names: `single` plants exactly one decision the spec neither states nor makes derivable, and `none` is a **zero-crux control** — every decision stated or derivable — authored to pair with one, and so nothing like a baseline task, which declares no construction at all. K12's four rungs (`criterion` → `repo-primitive` → `unmentioned` → `prose`) are the one ladder whose *order* is itself a pre-registered claim rather than a vocabulary: how the single withheld decision reaches the solver, hardest last, prose below unmentioned because prose displaces the module as the source of truth. Where a task declares K12, K1 is read over the spec's *other* decisions — K12 scopes the crux out of it — so a K12 family can hold K1 constant by writing every non-crux decision identically in every variant.
- **construction** — the block in a task's `task.yaml` recording how the task was built: its knob activations, its **difficulty prediction**, its **task family** where it belongs to one, and — for a vendored starting repository — its **substrate provenance**. Validated by the task model, required by the lint on every task outside the baseline that is not a **declared control**, and refused on every task inside it. It also carries a **pair** id where the task is one of two meant to be read against each other — either a planted crux and the zero-crux control built beside it, or two rungs of one enumerated ladder read against each other, as K12's families pair `prose` against `unmentioned` and `repo-primitive` against `criterion` — which the lint holds to exactly two members starting from the same repository, classified into the same capability-matrix cell, and setting the same knobs with exactly one of them varied, so that pairing is recoverable from the task set instead of from a table kept beside it. That last rule is the family rule over again and for the same reason — the rung delta the report prints for a pair is attributed to the one knob that moved — plus the case a family cannot have: members declaring *different* knobs, which reconciliation can only render as a crux/control contrast with one side at a level of `-`. The report's `crux` and `control` columns name the two members by their place on the varied knob's ladder — the higher level and the lower — which for a K9 pair is literally the planted crux and its control, and for a ladder pair is the rung predicted harder and the one predicted easier: K12's `unmentioned` prints as the `control` its `prose` partner is read against without anything having been planted in either.
- **zero-knob baseline** — the 22 tasks authored before the knob experiment. They carry no construction block, and that absence *is* their declaration: reconciliation reads round-1 outcomes against them as controls. The set is frozen in code, so a new task cannot join it by omission — a new task says it with a **declared control** instead.
- **declared control** — a task that says outright that it claims nothing about difficulty: `control: true` in its `task.yaml`, no **construction** block, and therefore no knob activations and no **difficulty prediction**. What a task authored to fill a **category** rather than to move a knob declares, and the only way to be a control outside the frozen 22. How it differs from the **zero-knob baseline**: those 22 declare it by the *absence* of a block, which is exactly why that set had to be frozen, since an absence is what an unfinished `task.yaml` has too. So the rule outside the frozen set is that a task declares one of the two and a task declaring neither is refused: **a control is declared and never inferred from an absence**. Declaring both is refused as well, because knob activations are the difficulty claim a control is the absence of. Where the two kinds of control are read alike is everywhere a control is read — the **calibration view**'s cost denominator, reconciliation's baseline effort comparator, its knob-grouping baseline rows and its single-level separation comparison — and in all of them a declared control counts in its own category and in no other, so a category the frozen 22 never reached is priced off the controls it declares.
- **task family** — several task directories (at least two) built from one underlying change, varying exactly one knob and holding everything else constant (repo, grading tests, diff target). Variants are self-contained directories sharing a naming stem and a family id; the starting repositories and grading suites are identical copies, because self-containedness beats deduplication — and the lint reads them byte for byte, since copies drift silently. Their taxonomy annotations (category, scale, language) must agree too, or one family's variants scatter across capability-matrix cells that are never compared. What must *not* be identical is the prompt: with everything else held constant it is where a spec-side knob actually moves, so two variants sharing one prompt declare a gradient the agent never sees. The levels a family sets must be distinct, or a variant is duplicated rather than added, but they need not cover the whole ladder: a three-variant K8 family (covered → bare → misleading) simply says less than a full sweep would, which is the author's call.
- **difficulty prediction** — the task author's pre-registered expectation, recorded before the task's first paid run: the **rung** of the operational difficulty ladder it should land on (`haiku-solvable` / `sonnet-only` / `unsolved`) plus a one-line rationale, and optionally an **effort claim**. Pre-registration is what makes the knob theory falsifiable rather than fitted to the sweep afterwards; the raw run log's append-only timeline is the audit trail that the prediction came first, and the rationale is what a missed prediction teaches (not: estimate, difficulty score).
- **effort claim** — the half of a **difficulty prediction** that bets on price rather than on outcome: a **comparator** (the task's pair partner, or the **zero-knob baseline** of its own category), a **metric** (`turns` or `cost` — register `cost` unless there is a reason to register `turns`) and a minimum factor above 1.0. `cost` is what to register because turns quantize: turn counts here are small integers, so from a 4-turn comparator the smallest possible step is exactly 1.25× and a 1.25× turns claim is met by one extra turn there while needing two against an 8-turn comparator — a stringency nobody registered. Cost is continuous and accumulates the reading, thinking and retrying that happen inside a turn. `turns` stays available and the field stays required, because a metric that defaulted silently would make an old claim read as a bet its author did not place. It exists because effort is where this experiment's signal has actually shown up — twice now turns and cost have separated where `resolved` could not — and recovering that from the logs afterwards is mining, not a result. Reconciliation grades it per model, because a run log measures one turns and one cost per task × model and a knob moves them by different multiples on different models: **hit** when the task's own measurement is at least the factor times its comparator's, **miss** when it is not, and **not assessable** when a run on either side is missing or when the comparator measured zero — an unswept comparator is an absent measurement and is never read as a claim that came out false, and no multiple of zero is anything, so a claim read against a zero is unreadable rather than trivially met. The baseline comparator is a **mean** over the controls that ran the model, not a median: at the few tasks per cell this experiment runs at, a median discards the tail the effort signal lives in. Optional, and its absence claims nothing: a task registering no effort claim is not registering that its knob is free. The claim's shape is checked where it is read — a claim against a pair partner on a task declaring no pair never loads — and the lint checks the half only the set can show, that a baseline claim's category actually has controls in the set.
- **observed rung** — where a task's runs actually put it, against which its **difficulty prediction** is scored: the rung named after the *weakest* model that resolved it (`haiku-solvable` beats `sonnet-only` even when both models resolved it), `unsolved` when none did. Two more states are not rungs and are never scored: a task no log mentions is `unswept`, and one whose runs cannot decide between two rungs — sonnet resolved it but haiku never ran — is `incomplete`. Withholding those beats guessing: reading a missing weaker model as a failure would invent a separation the sweep never measured.
- **round** — one sweep, identified by the **sweep id** its runs carry: the identifier the live runner stamps on every row of one invocation batch, named by the operator rather than derived, so that the several invocations one sweep takes (its models run apart, a resume after a crash) count as the one round they were. Runs logged before the field existed carry no id and fall back to the as-of date they ran on — the weaker key the id replaced, because it merges two sweeps run in one day and splits one that ran past midnight. Both keyings can appear in one reconciliation, which is why it labels a round `sweep <id>` or `as-of <date>` and reports how many of each it counted. A task × agent × model cell is only ever swept once (duplicate runs are schema-forbidden), so a second round is a sweep of *further* tasks, not a re-run of the same ones. What the kill discipline counts: a knob silent across two rounds it was asked in is demoted — where "asked in" is a round holding a **registered contrast** of it, and "silent" is neither **upward separation** nor an effort-claim hit.
- **reconciliation** — the read-only report (`ai-bench reconcile-v1`) that reads the raw run logs and the task set and says what the predictions were worth: per-task hit or miss with the registered rationale echoed on each miss, outcomes grouped per knob and level against the **zero-knob baseline** of the same category, each **task family**'s rungs in ladder order with a monotonicity check, each **pair**'s crux-versus-control rung delta, a **no-separation flag** per knob per round, and every registered **effort claim** graded per model. The effort section comes last and is numbered after the five that predate it rather than beside the rung reconciliation it belongs with by subject: the report is read by diffing one round's against the last one's, so renumbering to insert a section would move every line of it. It merges no record and appends to no log; the observed rungs come from replaying each logged diff against the task's held-out tests, exactly as `eval-v1 --replay` grades, because a run-log row carries the diff but no verdict. That is the cheapest reading that keeps every number recomputable from checked-in artifacts by one command.
- **registered contrast** — a comparison the *task set itself* declares, and the only thing the kill discipline counts a knob's rounds off (design note section 9, as amended in round 3). Two things are registered contrasts: a **task family** or **pair** swept in the round whose **varied knob** this is, and an **effort claim** registered on a task activating it *and scored to it*, read against the comparator that claim named — scored the way the **no-separation flag** entry sets out, so a pair claim on a task activating two knobs registers nothing about the knob its pair holds constant. A knob's level read against the frozen **zero-knob baseline**'s rung set is not one — the baseline was swept once, in an earlier round, against tasks nobody built to be read against this level — and neither is activating a knob without registering anything about it. What separates the two cases is registration and not the comparator: an author who writes a comparator, a metric and a factor into a construction block before the run can lose the bet.
- **upward separation** — the only kind of separation that counts. Order a registered contrast's levels on the knob's ladder; it separates when some harder level's **highest observed rung stands strictly above** some easier level's highest observed rung. A set difference on its own is not separation: under the direction-blind criterion this replaced, any level that resolved uniformly differed from a spread comparison and read as the knob working, which is how K11 — commissioned to push tasks *up* — was credited for coming out easier. Where the knob's ladder is not enumerated, no level is the harder one and the contrast is **not assessable**, for the same reason a pair on an unenumerated ladder names no crux. So is a contrast whose members do not all declare the knob: the **task-set lint** refuses that shape at authoring time, and where a replayed artifact carries one anyway the undeclared side has no rung to be ordered against, so the report names the member that does not declare the knob and reads no direction — rather than reporting a ladder it has enumerated as unenumerated, or reading the undeclared side as below the lowest rung, which on a ladder whose bottom rung already means *off* (K9's `none`) would separate two states that mean the same thing. The minimum-sample guard applies here too, turned in this reading's direction: where the harder side of every comparison a contrast could draw holds fewer graded tasks than the easier side has distinct rungs, its silence is an unbalanced sample as much as a quiet knob and the contrast is not assessable rather than silent.
- **no-separation flag** — reconciliation's report that a knob moved nothing in a round it was actually asked in. A counted round is **non-silent** when a **registered contrast** of that knob showed **upward separation**, or when any **effort claim** scored to that knob hit on any model — a pair claim scoring to the pair's varied knob, a baseline claim to the one knob its task activates where that is exactly one, and to no knob where the task activates several, because one reading over several knobs names none of them. Otherwise the round is silent, and the design note's two silent rounds still demote. Silence needs a reading that could have spoken: a round whose contrasts are all unreadable and whose claims are all **not assessable** prints not assessable and advances nothing. A round that put the knob to no registered contrast is not counted at all: a knob with no counted round prints as **stalled**, not silent, because it has not been shown to move nothing — it has never been asked, and demoting it would be reading a verdict off evidence nobody collected. The comparisons this report draws rather than the task set declaring them — a knob's levels read against each other within a round, or against the frozen zero-knob baseline where the round swept only one of them — are still **printed**, labelled informational and advancing no counter, because they remain the widest view of where a level landed; they carry the older direction-blind set comparison and its minimum-sample guard, which reports **not assessable** where a side of n graded tasks faces more than n distinct rungs and so could not have matched however its runs came out. The kill discipline's count is read against the round labels the report prints, not taken on its own: a **round** keyed on a sweep id is exactly one sweep, but a legacy round keyed on an as-of date may be two sweeps of one day counted once, or one sweep past midnight counted twice. A demotion names the rounds it counted, with their dates, because it travels out of the report into the design note.
- **substrate** — the starting repository seen as raw material: hand-authored (an artifact we made) or a cold OSS repository vendored as a snapshot tree at a pinned commit and then surgically edited to set terrain knobs. **Substrate provenance** records origin URL, the pinned commit, the license, and every **modification**, each naming the knob it sets — and that knob must be one the task itself activates, because an edit answering to no declared knob is difficulty the task's profile does not account for.
- **knob-activation profile** — the set of knob activations a task declares, read as one key and sorted by knob number: `K1=intent,K9=single`, and nothing else about the task. It is the axis the **calibration view** crosses with the task's category to make a row, which is why the order is normalized — a profile is a set, so two tasks activating the same knobs at the same levels are one cell however their construction blocks happened to list them, and a key that kept the authoring order would split that cell in two and halve both its counts. A task with no construction block has the **zero-knob** profile, and since the lint holds those to the frozen **zero-knob baseline** and every **declared control**, that profile's tasks are exactly the controls.
- **calibration view** — the read-only table (`ai-bench calibrate-v1`) that is the table side of the actuarial loop, and the first artifact of this project a selection query has something real to read: rows of task category × **knob-activation profile**, each carrying, per model on the operational ladder, a **cost multiplier** — the cell's mean run cost over the mean cost of the *same* category's zero-knob controls that ran that model, every logged run counted whether it resolved or not, because a run that failed still spent its dollars — and the cell's **rung floor**, the weakest **observed rung** any graded task in it landed on. Every reading prints the **n** it was taken over: a multiplier over two tasks and one over eleven are not the same claim, and a table that printed them alike would say they were, and the row's own task count is a third number the header names apart from those two. Its provenance discipline is **reconciliation**'s, by sharing that code path: run logs and task set read and never written, rungs obtained by replaying each logged diff against the held-out tests, no record merged — so every number in it is recomputable from checked-in artifacts by one command. ADR-0001's grouping rule reaches it through that shared reading, which selects one **agent**'s rows from the logs it is given before it checks anything — `--agent` on both readers, defaulting to `claude-code`, so one log directory can hold both harnesses' rows while a reading stays one harness's, and an agent named explicitly that no row carries is refused before anything is graded — and then refuses a model the operational ladder does not name. What v1 **refuses** is as much of the contract as what it prints, because a consumer cannot tell a measured cell from a filled-in one: no interpolation between a knob's levels, no backoff to a coarser key where a cell is thin, and no pooling of one category's controls into another category's denominator — the v1 contract the actuarial-loop design sets for this table, and why it prints a table per category rather than one table with a category column: a refactor control is not a feature-dev control. A cell nothing measured prints a dash and is listed with what was missing. What the row key does *not* carry is **disclosed** rather than keyed on, because the design's own primary key is category × **scale** and this one is category × profile: each table prints the scope and substrate **mix** of the controls its multipliers are divided by, and every row whose own mix differs prints it, so that a multiplier read across a scope difference — or a vendored cell read against hand-authored controls, which is every vendored cell, since **substrate provenance** is declared inside a **construction** block and a control carries none — is visibly that rather than the knob's price alone. Backoff is a real requirement of the actuarial design — it is how a sparse table still answers — but it has to arrive declaring the reduced confidence it answered at, and a v1 that quietly filled cells would publish numbers no sweep produced.

## Provenance vocabulary

- **source** — where a record's number came from: a URL, report name, or run id (not: origin, provider).
- **source type** — how the number was produced: `first-party` (we ran it, exact measurements), `per-instance` (second-hand but instance-level), `aggregate` (second-hand summary number only).
- **confidence** — how much a record should be trusted when views weight or filter: `high` / `medium` / `low`. First-party records are high by construction; see ADR-0001 for the model.
- **as-of date** — when the underlying result was produced (not when we ingested it). Views must surface it; stale data is shown, never hidden.
